ADR-012: Core0 Ringbuffer Processing Separation

Status: ACCEPTED
Date: 2025-08-19
Deciders: Architecture Team
Consulted: Senior Developer
Informed: Development Team

Context

Following the ringbuffer implementation in Issue #68 (ADR-011), the Core0 integration currently mixes two distinct concerns in the core0_process_uart() function:

  1. UART Hardware Processing: Managing actual UART hardware, RX/TX operations, DMA transfers, and interrupt handling

  2. Ringbuffer Message Processing: Dequeuing TCP→UART messages from the ringbuffer and echoing them back as UART→TCP messages

This architectural mixing violates separation of concerns and makes the system harder to maintain and test. The current implementation also doesn’t follow the same architectural pattern as Core1, which properly separates different types of work through distinct states and functions.

Current Core0 Architecture Problems: * Mixed UART hardware and ringbuffer processing in single function * Inconsistent with Core1’s work separation pattern * Difficult to unit test individual concerns * No clear distinction between hardware and message processing states * Missing check_for_pending_work() pattern that Core1 uses

Core1 Reference Pattern: Core1 properly separates concerns with: * core1_work_or_idle_wait() → calls check_for_pending_work() * check_for_pending_work() → inspects various work queues and fires appropriate events * Distinct states for different work types: CORE1_NET_ACTIVE_RECEIVE, CORE1_LOG_ACTIVE, CORE1_PERSISTENCE_ACTIVE * Clear separation between checking for work and executing work

Decision

Refactor Core0 to separate UART hardware processing from ringbuffer message processing using the same architectural pattern as Core1.

New Core0 Architecture

New Core0 Operational States:

typedef enum {
    // Initialization states (unchanged)
    CORE0_INIT_UART,
    CORE0_INIT_COMPLETE,
    CORE0_INIT_IDLE,
    CORE0_INIT_ERROR,

    // Configuration states (unchanged)
    CORE0_CONFIG_UART,
    CORE0_CONFIG_COMPLETE,
    CORE0_CONFIG_IDLE,
    CORE0_CONFIG_ERROR,

    // NEW: Operational states (separated concerns)
    CORE0_IDLE,                    // Check for work or sleep (like Core1)
    CORE0_UART_ACTIVE,            // UART hardware processing only
    CORE0_RINGBUFFER_ACTIVE,      // Ringbuffer message processing only
    CORE0_UART_ERROR              // UART hardware error handling
} core0_substate_t;

New Core0 Events:

typedef enum {
    // Existing events (unchanged)
    CORE0_EVENT_INIT_UART_COMPLETE,
    CORE0_EVENT_INIT_UART_FAILED,
    CORE0_EVENT_CONFIG_UART_COMPLETE,
    CORE0_EVENT_CONFIG_UART_FAILED,
    CORE0_EVENT_UART_ERROR,
    CORE0_EVENT_ERROR_RECOVERED,
    CORE0_EVENT_AUTO_TRANSITION,

    // NEW: Separated work events
    CORE0_EVENT_UART_DATA_READY,       // UART hardware has data to process
    CORE0_EVENT_UART_WORK_COMPLETE,    // UART hardware work finished
    CORE0_EVENT_RINGBUFFER_DATA_READY, // Ringbuffer has messages to process
    CORE0_EVENT_RINGBUFFER_WORK_COMPLETE, // Ringbuffer work finished
    CORE0_EVENT_WORK_IDLE              // All work completed, return to idle
} core0_event_t;

New Function Architecture

Main Loop Integration (following Core1 pattern):

case MAIN_STATE_OPERATIONAL:
    switch (sub_state) {
        case CORE0_IDLE:
            core0_work_or_idle_wait();     // NEW: Check for work or sleep
            break;
        case CORE0_UART_ACTIVE:
            core0_process_uart_hardware(); // NEW: UART hardware only
            break;
        case CORE0_RINGBUFFER_ACTIVE:
            core0_process_ringbuffer();    // NEW: Ringbuffer messages only
            break;
        case CORE0_UART_ERROR:
            core0_handle_uart_error();     // Unchanged
            break;
    }
    break;

Core0 Work Detection (following Core1 pattern):

static bool core0_check_for_pending_work(void) {
    // Check for ringbuffer messages to process (highest priority)
    if (ringbuffer_get_count(RX_TCP_TO_UART) > 0) {
        state_machine_process_core0_event(CORE0_EVENT_RINGBUFFER_DATA_READY);
        return true;
    }

    // Check for UART hardware work (medium priority)
    if (uart_hardware_has_pending_work()) {
        state_machine_process_core0_event(CORE0_EVENT_UART_DATA_READY);
        return true;
    }

    // No work pending
    return false;
}

static void core0_work_or_idle_wait(void) {
    // Check for work first
    if (core0_check_for_pending_work()) {
        return; // Work found, event fired, let state machine handle it
    }

    // No work, go to sleep
    core0_idle_wait();
}

Separated Processing Functions:

// NEW: Process ringbuffer messages only (moved from core0_process_uart)
static void core0_process_ringbuffer(void) {
    // Dequeue TCP→UART message and echo back as UART→TCP
    ring_entry_t* tcp_to_uart_msg = ringbuffer_dequeue_entry(RX_TCP_TO_UART);
    if (tcp_to_uart_msg) {
        // Turn around the message
        tcp_to_uart_msg->direction = RX_UART_TO_TCP;
        bool success = ringbuffer_enqueue_entry(tcp_to_uart_msg);

        log_event(EVENT_SOURCE_RINGBUFFER, LOG_LEVEL_DEBUG,
                  success ? LOG_EVENT_RINGBUFFER_ECHO_SUCCESS : LOG_EVENT_RINGBUFFER_ECHO_FAILED, 1);
    }

    // Work complete
    state_machine_process_core0_event(CORE0_EVENT_RINGBUFFER_WORK_COMPLETE);
}

// NEW: Process UART hardware only (cleaned up from core0_process_uart)
static void core0_process_uart_hardware(void) {
    // Handle actual UART hardware operations
    if (process_uart_data()) {
        log_event(EVENT_SOURCE_UART0, LOG_LEVEL_DEBUG, LOG_EVENT_UART_COMPLETE, 0);
        state_machine_process_core0_event(CORE0_EVENT_UART_WORK_COMPLETE);
    }
    // If processing not complete, remain in UART_ACTIVE state
}

New Log Events

Core0-Specific Log Events:

// New ringbuffer processing events
LOG_EVENT_RINGBUFFER_ECHO_SUCCESS = 410,    // Ringbuffer message echoed successfully
LOG_EVENT_RINGBUFFER_ECHO_FAILED = 411,     // Ringbuffer message echo failed
LOG_EVENT_RINGBUFFER_WORK_START = 412,      // Ringbuffer processing started
LOG_EVENT_RINGBUFFER_WORK_COMPLETE = 413,   // Ringbuffer processing completed

// New Core0 state events
LOG_EVENT_CORE0_WORK_CHECK = 420,           // Core0 checking for pending work

LOG_EVENT_CORE0_UART_WORK_START = 422,      // UART hardware work started
LOG_EVENT_CORE0_UART_WORK_COMPLETE = 423,   // UART hardware work completed

Rationale

Why Separate UART Hardware from Ringbuffer Processing

Clear Separation of Concerns: * UART hardware processing deals with physical hardware, interrupts, DMA, and real-time constraints * Ringbuffer processing deals with message-level logic, echo functionality, and inter-core communication * Each can be unit tested independently with appropriate mocks

Consistent Architecture: * Follows same pattern as Core1 with check_for_pending_work() and distinct work states * Makes the codebase more maintainable and understandable * Enables future extensions like different ringbuffer processing modes

Performance Benefits: * Allows prioritization of ringbuffer work over UART hardware work * Enables fine-grained performance monitoring of each concern * Prevents blocking of one concern by the other

Why Follow Core1 Pattern

Architectural Consistency: * Both cores now follow the same work_or_idle_wait() → check_for_pending_work() → specific work pattern * Similar state machine structures with IDLE state for work detection * Consistent event naming and processing patterns

Proven Design: * Core1 pattern has been tested and works reliably * Well-understood by the development team * Provides good separation of concerns and testability

Implementation Strategy

Phase 1: Update Documentation and Interfaces

  1. Update state_machine.h: Add new Core0 states and events

  2. Update log_manager.h: Add new Core0-specific log events

  3. Update this ADR: Document the complete new architecture

Phase 2: Write Tests (TDD Approach)

  1. Test Core0 State Transitions: Test new IDLE → UART_ACTIVE/RINGBUFFER_ACTIVE transitions

  2. Test Work Detection: Test core0_check_for_pending_work() logic with various work conditions

  3. Test Separated Processing: Test core0_process_ringbuffer() and core0_process_uart_hardware() independently

  4. Test Integration: Test complete flow from work detection to work completion

Phase 3: Implement Production Code

  1. Refactor core0_main.c:

    • Move ringbuffer processing from core0_process_uart() to new core0_process_ringbuffer()

    • Add core0_work_or_idle_wait() and core0_check_for_pending_work()

    • Update state machine integration in main loop

  2. Update state_machine.c: Add new state transitions and event processing

  3. Update log strings: Add log format strings for new events

Phase 4: Testing and Validation

  1. Unit Testing: Verify all functions work correctly in isolation

  2. Integration Testing: Test complete Core0 operation with real ringbuffer

  3. Performance Testing: Ensure no performance regression from refactoring

  4. Protocol Validator: Validate echo functionality still works correctly

Consequences

Positive

  • ✅ Clear Separation of Concerns: UART hardware and ringbuffer processing are cleanly separated

  • ✅ Architectural Consistency: Core0 now follows same pattern as Core1

  • ✅ Better Testability: Each concern can be unit tested independently

  • ✅ Improved Maintainability: Easier to understand and modify individual concerns

  • ✅ Performance Monitoring: Can measure performance of UART vs ringbuffer processing separately

  • ✅ Future Extensibility: Easy to add new types of Core0 work (e.g., protocol filtering)

Negative

  • ❌ Code Complexity: More states and functions to manage

  • ❌ Development Time: Requires refactoring existing working code

  • ❌ Testing Overhead: More test cases needed for additional states and transitions

Risks and Mitigation

Primary Risk: Functional Regression * Probability: Low (careful TDD approach) * Impact: High (break existing echo functionality) * Mitigation: Comprehensive unit and integration testing, protocol validator validation

Secondary Risk: Performance Regression * Probability: Low (no fundamental algorithm changes) * Impact: Medium (slower echo response times) * Mitigation: Performance testing with protocol validator, benchmark comparison

Success Criteria

Functional Requirements: 1. ✅ Echo functionality maintains same behavior as before refactoring 2. ✅ UART hardware processing works independently of ringbuffer processing 3. ✅ Core0 follows same architectural pattern as Core1 4. ✅ All existing tests continue to pass 5. ✅ New unit tests achieve 100% coverage of new functions

Architectural Requirements: 1. ✅ Clear separation between UART hardware and ringbuffer concerns 2. ✅ core0_process_uart() only handles UART hardware 3. ✅ New core0_process_ringbuffer() only handles ringbuffer messages 4. ✅ core0_check_for_pending_work() pattern matches Core1 5. ✅ New states and events properly integrated into state machine

Quality Requirements: 1. ✅ No performance regression compared to current implementation 2. ✅ Protocol validator tests continue to pass 3. ✅ Code review approval from code quality and security specialists 4. ✅ Comprehensive logging of all state transitions and work processing
