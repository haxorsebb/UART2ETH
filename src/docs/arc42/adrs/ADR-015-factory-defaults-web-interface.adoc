= ADR-015: Factory Defaults Web Interface

== Status
Accepted

== Date
2026-01-21

== Context

The factory defaults system (ADR-014) requires a manufacturing interface to program device-specific configuration data during production. Manufacturing operators need a simple, reliable method to write factory defaults without command-line tools or external programmers.

Key requirements:
* Simple web-based interface accessible from production floor
* Input validation to prevent manufacturing errors
* Read-back verification after programming
* Only available in factory firmware builds
* Minimal external dependencies

Manufacturing workflow requires:
* Serial number input (decimal format with leading zeros)
* MAC address configuration
* Board type selection
* Default network configuration
* Factory password setting
* Immediate verification of programmed data

== Decision

We will implement a web-based factory defaults programming interface accessible at `/factory` that is only compiled when `FACTORY_INTERNAL_VERSION` is defined.

### Interface Design

**Route Structure**
* `GET /factory` - Display factory defaults configuration form
* `POST /factory` - Process and write factory defaults to flash

**Form Sections**
1. Serial Number Section
   - Production year (0-99, representing 2000-2099)
   - Production week (1-52)
   - Serial number (decimal, 0-281474976710655, displayed with leading zeros)
   - Real-time preview: "YYWW-NNNNNNNNNNNN"

2. Network Identity Section
   - MAC address (format: XX:XX:XX:XX:XX:XX)

3. Board Type Section
   - Radio buttons: SHARK (0), PRIMARY (1), SECONDARY (2)

4. Default Network Configuration Section
   - Default IP address (IPv4 format)
   - Default netmask (IPv4 format)
   - Default DHCP enable (checkbox)

5. Security Section
   - Factory default password (max 31 characters)

6. Actions Section
   - Write Factory Defaults (primary action)
   - Erase Factory Defaults (warning action)

**Validation Strategy**

Client-side validation (JavaScript):
* Real-time field validation with visual feedback
* Format validation for IP addresses and MAC addresses
* Range checking for year (0-99), week (1-52)
* Serial number decimal range validation
* Password length validation (max 31 chars)
* Disable submit until all fields valid

Server-side validation (C code):
* Re-validate all inputs before flash operations
* Return HTTP 400 with specific error messages on validation failure
* Range checking for all numeric fields
* String length validation for password

**Post-Write Verification**
After successful write operation:
1. Reload factory defaults from flash
2. Validate integrity (SHA256 check)
3. Display programmed values in read-only format
4. Show formatted serial number for verification

## Rationale

### Advantages
* **Ease of Use**: Web interface requires no special tools or software installation
* **Error Prevention**: Client-side validation prevents most input errors before submission
* **Verification**: Automatic read-back confirms successful programming
* **Production Efficiency**: Fast, simple interface for manufacturing floor
* **Compile-Time Safety**: Factory functions only available in factory builds
* **Consistent UX**: Matches existing configuration page design

### Rejected Alternatives

**Command-Line Tool**
* Rejected due to complexity for manufacturing operators
* Requires USB connection and terminal software
* Higher error rate for manual hex/decimal input
* Slower workflow

**External Programmer**
* Rejected to avoid additional hardware requirement
* Network-based programming simpler for production line
* Web interface provides immediate visual feedback

**Separate Manufacturing Application**
* Rejected to minimize tooling complexity
* Built-in web interface eliminates installation requirements
* Consistent with existing web-based configuration

### Trade-offs
* **Firmware Size**: Additional HTML generation code only in factory builds
* **Code Complexity**: Form validation logic adds complexity but prevents errors
* **Network Requirement**: Requires network connection for programming (acceptable for manufacturing)

== Consequences

### Positive
* **Simplified Manufacturing**: Web interface reduces operator training requirements
* **Error Reduction**: Validation prevents common manufacturing errors
* **Fast Verification**: Immediate read-back confirms programming success
* **No External Tools**: Eliminates need for separate programming software
* **Audit Trail**: Programmed serial numbers visible in boot logs

### Negative
* **Factory Build Required**: Must build separate firmware for manufacturing
* **Code Size**: Additional HTML generation increases factory firmware size
* **Network Dependency**: Requires working network connection for programming

### Implementation Requirements
* Add `/factory` route to HTTP server
* Implement `http_generate_factory_page()` for form display
* Implement `http_parse_factory_post_data()` for processing
* Add client-side JavaScript validation
* Guard all factory code with `#ifdef FACTORY_INTERNAL_VERSION`
* Add read-back verification after write
* Update HTTP server documentation

== Implementation Notes

The factory defaults web interface will be implemented as an extension to the existing HTTP server module. Form generation and processing follow the same pattern as the `/config` page.

Integration points:
1. **http_server.c**: Add `/factory` route handling
2. **http_server.c**: Implement factory page generation
3. **http_server.c**: Implement factory POST data parsing
4. **factory_defaults.c**: Utilize existing write/erase functions

### HTML Generation Strategy
* Inline CSS matching existing configuration page style
* Embedded JavaScript for client-side validation
* Form fields organized into logical sections
* Visual feedback for validation errors
* Confirmation dialogs for write/erase operations

### Validation Implementation
* Serial number: Decimal input (0 to 281474976710655), displayed as 12-digit zero-padded
* Production year: Range 0-99
* Production week: Range 1-52
* MAC address: Parse format XX:XX:XX:XX:XX:XX or XX-XX-XX-XX-XX-XX
* IP addresses: Standard IPv4 validation
* Password: Maximum 31 characters (null terminator required in 32-byte buffer)

### Error Handling
* Validation errors: Display specific error per field, prevent submission
* Flash write errors: Return HTTP 500 with error details
* Read-back mismatch: Display warning, show programmed vs. expected values
* Partition errors: Return HTTP 500 with diagnostic information

### User Experience Flow
1. Operator navigates to `http://<device-ip>/factory`
2. Form displays with empty/default values
3. Operator fills manufacturing data
4. Real-time validation provides feedback
5. Operator clicks "Write Factory Defaults"
6. Confirmation dialog shows all values
7. Server writes to flash and verifies
8. Success page displays programmed data with formatted serial number
9. Operator verifies serial number matches production database
