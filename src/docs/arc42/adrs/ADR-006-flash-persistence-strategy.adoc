= ADR-006: Flash Persistence Strategy

== Status
Accepted

== Date
2024-01-15

== Context

The UART2ETH system requires persistent storage of configuration data to survive power cycles and system resets. The configuration includes UART channel settings, network parameters, user accounts, and system preferences stored in the `g_shared_memory` structure.

Key requirements:
* Embedded system constraints (limited flash, no external storage)
* Power-loss safety (industrial environment)
* Flash wear leveling (device longevity)
* Fast startup times (minimize boot delays)
* Simple implementation (avoid complex file systems)
* Integrity verification (detect corruption)

== Decision

We will implement flash persistence using an **8-block ring buffer strategy** with **RP2350 partition table isolation** for industrial reliability:

### Flash Partitioning Strategy
* **RP2350 Partition Table**: Use native partition system for true isolation
* **Configuration Data Partition**: Dedicated data partition (ID=3) discovered via bootrom APIs
* **A/B Firmware Isolation**: Firmware updates never touch configuration partition
* **Industrial Safety**: `"ignored_during_arm_boot": true` prevents accidental erasure

### Storage Format
* **Raw binary storage**: Direct copy of `shared_memory_layout_t` structure to flash
* **No JSON or schema validation**: Eliminates parsing overhead and complexity
* **Complete structure per block**: Atomic writes of entire configuration
* **Embedded shared memory**: Shared memory is statically allocated within a flash persistence block structure

### Ring Buffer Management
* **8 Configuration Blocks** organized as circular ring buffer within data partition
* **Block size**: 64KB per block (16 × 4096-byte flash sectors)
* **Wear leveling**: Sequential writes advance through ring, sector-by-sector updates
* **Block metadata**: SHA256 checksum (first field) + magic number + revision counter per block
* **Magic number**: Block validity marker (`0xC0FFEEAA`)
* **Partition discovery**: Runtime partition table lookup via bootrom APIs

### Write Strategy
* **Deferred write-back**: Integrated into Core1 main loop
* **Frequency limiting**: Maximum once per 30 seconds
* **Change detection**: Write only when `revision_counter` increments
* **Sector-level updates**: Only changed sectors within a block are erased and reprogrammed
* **Safe flash operations**: Uses `flash_safe_execute()` for interrupt-safe flash access
* **Write-in-progress tracking**: Prevents concurrent write operations

### Recovery Process
* **Startup validation**: Read all 8 blocks, verify checksums
* **Block selection**: Use block with highest revision + valid checksum
* **Corruption handling**: Skip invalid blocks, fallback to factory defaults
* **Error logging**: Track corruption events for diagnostics

## Rationale

### Advantages
* **Power-loss safety**: Sector-by-sector writes with checksums prevent partial corruption
* **Wear leveling**: Ring buffer distributes writes across 8 blocks
* **Fast recovery**: Simple page validation, no complex parsing
* **Integrity verification**: SHA256 detects any data corruption
* **Embedded-friendly**: No file system overhead or external dependencies
* **Deterministic behavior**: Known write patterns, predictable performance

### Rejected Alternatives

**File System Approach**
* Rejected due to complexity and flash overhead
* Would require FAT or custom file system implementation
* Higher RAM usage for file system structures

**JSON Configuration Files**
* Rejected due to parsing overhead and complexity
* Would require JSON parser library (code size increase)
* Schema validation adds unnecessary complexity for embedded use

**A/B Partition Strategy**
* Rejected as insufficient for wear leveling
* Only 2 locations would wear out faster
* No automatic progression through multiple backup copies

**EEPROM External Storage**
* Rejected to avoid additional hardware components
* Increases BOM cost and PCB complexity
* RP2350 internal flash sufficient for configuration data

### Trade-offs
* **Flash usage**: 8 × 64KB blocks for configuration ring buffer
* **Write frequency**: Limited to 30-second intervals (acceptable for config changes)  
* **Recovery time**: Startup requires reading/validating 8 blocks (minimal impact)
* **Partition complexity**: Requires RP2350 partition table support in build system

== Consequences

### Positive
* **Partition Isolation**: Configuration data completely isolated from firmware updates
* **A/B Update Safety**: Software updates never risk configuration data corruption
* **Industrial Reliability**: RP2350 partition table provides true isolation guarantees
* **Future Growth**: Partition size determined by partition table, allows expansion
* **Automatic wear leveling**: Ring buffer distributes writes across 8 blocks
* **Simple implementation**: Raw binary storage reduces bugs and maintenance
* **Fast startup**: Minimal validation overhead with integrity verification
* **Power-loss safety**: Atomic snapshot writes prevent partial corruption

### Negative
* **Flash usage**: 8 × 64KB blocks reserved for ring buffer
* **Write frequency**: Limited to 30-second intervals (acceptable for config changes)
* **Build complexity**: Requires partition table embedding in build system
* **Sector-level granularity**: Updates are sector-by-sector within blocks, but still writes complete block metadata

### Implementation Requirements
* Flash operations abstraction layer for RP2350 with partition awareness
* SHA256 hash implementation for integrity verification
* Integration with Core1 main loop for deferred writes
* Factory reset capability for complete corruption recovery
* Configuration Snapshot format definition and serialization functions

== Implementation Notes

The persistence system will be integrated into the existing shared memory module rather than implemented as a separate component. This maintains architectural simplicity while providing the required functionality.

The `revision_counter` in `g_shared_memory` serves dual purposes:
1. Coordination between cores for configuration changes
2. Flash persistence trigger and page selection during recovery

== Detailed Implementation Strategy

### Partition Table Integration
* **RP2350 Bootrom APIs**: Use `rom_get_partition_table_info()` for partition discovery
* **No Raw Flash Offsets**: Leverage bootrom partition table parsing instead of manual calculations
* **Safe Flash Operations**: Use `flash_safe_execute()` for interrupt-safe flash erase/program
* **Partition Discovery**: Use partition ID=3 (FLASH_PARTITION_CONFIGURATION_DATA) to locate configuration data partition at runtime

### Hardware Crypto Implementation
* **SHA256 Engine**: Use pico-sdk `pico/sha256.h` hardware crypto APIs for integrity verification
* **RP2350 Hardware Acceleration**: Uses `pico_sha256_start_blocking()`, `pico_sha256_update_blocking()`, `pico_sha256_finish()`
* **Performance Optimization**: Hardware acceleration eliminates software SHA256 overhead
* **Checksum Placement**: SHA256 checksum placed first in block structure to simplify exclusion during hash calculation
* **Hash Coverage**: SHA256 covers all fields after the checksum (magic_number through padding)

### Core1 Integration Strategy
* **New Core1 Main Function**: Create `core1_main()` as entry point for Core1 processing
* **Lowest Priority Task**: Flash persistence checking runs after all other Core1 tasks
* **Deferred Write Logic**: Check for changes every 100ms, write only if 30+ seconds elapsed
* **Non-blocking Operation**: Persistence never blocks critical network or ring buffer operations

### Change Detection and Write Control
* **Static State Tracking**: Local static variable tracks last written `revision_counter` value
* **Change Detection**: Compare current vs. last written revision to detect config changes
* **Write Frequency Limiting**: Track last write timestamp, enforce 30-second minimum interval
* **Atomic Decision**: Only proceed with write if both change detected AND time interval met

### Error Handling and Recovery
* **Factory Reset Strategy**: If all 8 ring buffer blocks corrupt, load factory defaults via `shared_memory_force_reinit()`
* **Recovery Event Logging**: Use existing `log_event()` API to record factory reset as first entry
* **Graceful Degradation**: System continues operation with defaults if persistence fails
* **Corruption Detection**: SHA256 mismatch triggers recovery sequence with detailed error logging

### Ring Buffer State Management
* **8-Block Circular Buffer**: Blocks 0-7 in sequential write order with wrap-around at block 7→0
* **Block Selection Logic**: Write to next block in sequence, select highest revision during recovery
* **Write State Tracking**: Track current write block position in static state structure
* **Overflow Handling**: After block 7, wrap to block 0 for continuous wear leveling

### Memory Layout and Data Structures

```c
// Flash persistence block structure (64KB aligned, 16 × 4096-byte sectors)
// Note: sha256_checksum is placed first to simplify exclusion during hash calculation.
// The hash covers all fields after sha256_checksum (magic_number through padding).
typedef struct {
    uint8_t  sha256_checksum[32];             // Block integrity verification (FIRST for easy hash exclusion)
    uint32_t magic_number;                    // 0xC0FFEEAA block validity
    uint32_t revision_counter;                // Write sequence tracking
    uint32_t reserved[4];                     // Future expansion
    
    shared_memory_layout_t shared_memory_data; // Complete config snapshot
    
    uint8_t padding[...];                     // Padding to 64KB block size
} __attribute__((packed, aligned(4096))) flash_persistence_block_t;

// Ring buffer management state (runtime tracking, not persisted)
typedef struct {
    uint8_t  current_write_block;             // 0-7, next block to write  
    uint8_t  last_valid_block;                // 0-7, last successfully read
    uint32_t total_writes_lifetime;           // Total write operations
    uint32_t corruption_events;               // Detected corruption count
    uint32_t last_written_revision;           // Change detection state
    uint32_t last_write_timestamp_ms;         // Write frequency control
    uint8_t  active_config_partition_id;      // Current config partition (3)
    uint32_t partition_start_offset;          // Partition start address
    uint32_t partition_size;                  // Partition size in bytes
    bool     initialized;                     // Initialization status
    bool     write_in_progress;               // Prevents concurrent writes
} flash_persistence_state_t;

// Shared memory is statically allocated within a flash_persistence_block_t:
static flash_persistence_block_t aligned_block_including_logs 
    __attribute__((aligned(64 * 1024))) = {0};
static shared_memory_layout_t* g_shared_memory = 
    &(aligned_block_including_logs.shared_memory_data);
```

### Implementation Phases (Completed)

**Phase 1: Core Infrastructure** ✓
1. Created `flash_persistence.c` and `flash_persistence.h` implementation files
2. Implemented partition table discovery using bootrom APIs (`rom_get_partition_table_info()`)
3. Integrated hardware SHA256 via `pico/sha256.h`
4. Implemented 8-block ring buffer state management

**Phase 2: Core1 Integration** ✓
1. Persistence checking integrated as lowest priority Core1 task
2. Implemented change detection via revision counter comparison
3. Added 30-second write frequency limiting
4. Implemented sector-by-sector flash updates with `flash_safe_execute()`

**Phase 3: Recovery and Error Handling** ✓
1. Startup recovery validates all 8 blocks, selects highest valid revision
2. Factory reset erases all blocks and calls `shared_memory_force_reinit()`
3. Comprehensive error logging via `log_event()` API
4. Device mode enforcement after flash load (GPIO pins, channel enables)
